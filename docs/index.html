A daemon holds PTY / shell sessions on a machine. A client pairs by token, then creates or attaches. Sessions outlive both the client and the daemon — close your laptop, kill the daemon, come back from another device, and the shell is still there.

Why tyd

The shell survives. You just reattach.

Most remote shells die with the connection, the client, or the daemon. tyd is built around the opposite assumption.

♾️

Outlives client & daemon

Each session runs in its own process under ~/.tyd/live/. It keeps running across a tyd up restart — the next daemon adopts it again.

🔑

Pairs by token, not account

No account to create. The host mints a single-use invite, the peer runs tyd accept TOKEN. Invites expire after 10 minutes.

📦

One binary, both ends

The same binary is daemon and client. No SSH / VPN stack to configure — it layers on the network you already trust.

🏠

Self-hostable control plane

Control Panel and relay are both self-hostable, and --relay takes a list — you're not tied to one rendezvous point.

👁️

Watch without touching

tyd session watch follows a session read-only. Name sessions with aliases and reattach with a shortcut like tyd jammy.laptop.

🌐

Works over what you have

LAN, WireGuard, or Tailscale — tyd layers on top. Direct when it can, relay as a dual-NAT fallback when it can't.

How it works

Daemon → Session → Client

Three pieces, one idea: the shell's lifetime is independent of everything that connects to it.

01 — HOST

Daemon

tyd up listens on ~/.tyd/tyd.sock locally by default. It holds the sessions and gates remote peers.

→
02 — HOST

Session

Each shell lives in its own process under ~/.tyd/live/. Detach, disconnect, or restart the daemon — it keeps running.

→
03 — ANYWHERE

Client

Pair once with a token, then create or attach from any paired device. Ctrl-\ detaches and leaves the shell running.

On the host — holds the shells
# after install — the installer registers this host
tyd approval pre        # read by the daemon at start
tyd up
tyd invite              # mint a token (10 min); waits for the peer
tyd invite --no-wait    # mint & exit immediately
On the peer — your laptop, another machine
tyd accept TOKEN --as laptop
tyd --peer laptop session create
tyd session alias jammy
tyd jammy.laptop        # reattach, from anywhere
tyd session list / watch / close
Ctrl-\  detach — shell keeps running
session close  actually ends the session
EXITED ≠ gone  a shell that exits on its own is still attachable

Honest positioning · Security

Not a replacement. A different trade-off.

tyd doesn't claim to replace tmux + ssh, mosh, or Tailscale SSH. Read the full comparison — including where tyd adds nothing — in the docs.

vs. the tools you already know

ToolWhat it's great atWhere tyd differs
tmux + sshBattle-tested multiplexing inside an SSH session you already have.Sessions also survive a daemon restart, and pairing is by token — no SSH stack to configure.
moshRoaming, high-latency, flaky networks.tyd is about session lifetime & remote attach, not link resilience.
Tailscale SSHIdentity & access inside a tailnet.tyd layers on Tailscale / WireGuard / LAN instead of replacing the network.

🔒 Identity & transport

  • Ed25519 keys in ~/.tyd; every connection runs challenge-response against the peer's trusted.json. A new key needs explicit pairing.
  • TLS 1.3 minimum — pinned certificate fingerprint direct, or TLS 1.3 negotiated through the relay. The relay relays ciphertext and never sees session bytes.
  • Control Panel sees no TTY bytes — only daemon ids, public keys, and dial metadata.

🛂 Approval & audit

  • Approval modes: full (default), pre (approve each request — start here for a new peer), post.
  • Invites are single-use and expire in 10 minutes. Pressing Ctrl-C revokes.
  • Audit log (--audit-log FILE) records control events only — never terminal content.
  • Optional sandbox: tyd up --sandbox docker --sandbox-image IMAGE --sandbox-workdir DIR runs the shell in a container that sees only the workdir.

Local boundary, stated plainly in the README: a session runs as the same user as the daemon, so approval modes gate a remote peer — not code already running inside a session.

Install · Docs

One line. No sudo. Then read the docs.

Per-user install to ~/.local/bin/tyd, state in ~/.tyd. The installer verifies the archive against the release checksums.txt and refuses a mismatch. Windows is not supported.
